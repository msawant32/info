IMPORTANT: The BDK is the SAME key shared across ALL PIN pads in your organization (all Ingenico Lane 7000 devices at all branches). It's loaded during a secure key ceremony. The uniqueness comes from each device's unique KSN, not the BDK.

PCI-PTS certified PIN entry device with tamper-resistant secure cryptographic processor. Stores BDK in secure memory.
🔢 Initial KSN
Key Serial Number initialized with UNIQUE device ID and transaction counter set to 0. Format: Device ID (59 bits) + Counter (21 bits). THIS is what makes each device's keys unique, even though they all share the same BDK!
🔐 BDK Example:
BDK = 0123456789ABCDEFFEDCBA9876543210 (16 bytes / 128 bits)

🛡️ DUKPT Security Features
• Each transaction uses a unique, one-time encryption key
• Keys are never reused, even if PIN pad is compromised
• Forward security: Old keys cannot be derived from new keys
• Transaction counter increments with each use (max: 1,048,576 transactions)

🔄 HOW CARDBASE & HSM INTERACT (Detailed Flow)
Step-by-Step CardBase ↔ HSM Communication:

1. CardBase Receives Transaction:
• CardBase host receives encrypted PIN block + KSN from FIS Teller
• CardBase does NOT have cryptographic capabilities itself
• CardBase stores the BDK identifier (not the actual BDK value)

2. CardBase Calls HSM API:
• CardBase sends command to HSM: "PIN_TRANSLATE" or "PIN_VERIFY"
• Sends: Encrypted PIN block, KSN, BDK identifier, PAN (card number)
• Communication is over secure, authenticated connection

3. HSM Performs Cryptographic Work:
• HSM retrieves actual BDK from its secure key storage using the identifier
• HSM runs DUKPT algorithm: BDK + KSN → Derived Transaction Key
• HSM performs 3DES decryption using derived key
• HSM extracts clear PIN from PIN block
• CRITICAL: BDK never leaves the HSM's secure boundary!

4. HSM Returns Result to CardBase:
• Option A: Returns decrypted PIN (for CardBase to verify against database)
• Option B: HSM compares PIN itself and returns match/no-match (more secure)
• HSM logs the operation for audit purposes

5. CardBase Completes Transaction:
• If PIN matches: checks balance, approves transaction
• If PIN doesn't match: increments fail counter, declines transaction
• Updates account records and sends response back

⚠️ CRITICAL CONCEPT: BDK IS SHARED, KSN PROVIDES UNIQUENESS
Q: Is the BDK unique per device?
A: NO! The BDK is the SAME key shared across ALL devices in your organization (all branches, all Ingenico PIN pads).

Q: Then how are transactions secure and unique?
A: Each device has a unique KSN (Key Serial Number) that includes:
• Unique Device ID (embedded during manufacturing)
• Transaction Counter (increments with each transaction)

The Magic of DUKPT:
Even though 100 devices share the same BDK, DUKPT ensures that:
• Device #1 with KSN "FFFF9876543210E00001" generates Key A
• Device #2 with KSN "FFFF1234567890E00001" generates Key B (completely different!)
• Same device on transaction #2 generates Key C (also completely different!)

Why Share BDK Across Devices?
• Simplifies key management (one BDK to protect, not thousands)
• CardBase host only needs one BDK to decrypt from ALL devices
• Secure key loading ceremony happens once for the entire organization
• If a device is compromised, only that device's future keys are at risk

Real-World Example:
Your bank has 50 branches with 200 PIN pads total. All 200 devices have the same BDK loaded (maybe "BDK_ACME_BANK_2024"). But each has unique device IDs, so each generates completely different encryption keys for every transaction.

3DES: Triple Data Encryption Standard - Encryption algorithm
IPEK: Initial PIN Encryption Key - First derived key

PAN: Primary Account Number - Card number
PCI-PTS: Payment Card Industry PIN Transaction Security

🛡️ END-TO-END SECURITY SUMMARY
Key Security Features:
• PIN never exists in clear text outside the PIN pad's secure processor
• Unique encryption key for every single transaction (DUKPT)
• Keys are mathematically derived, never transmitted
• Triple encryption (3DES) for maximum security
• HSM ensures cryptographic operations are tamper-resistant
• Forward security: Compromising one key doesn't expose past or future transactions
• PCI-PTS certified hardware ensures physical security
• Transaction counter prevents replay attacks
